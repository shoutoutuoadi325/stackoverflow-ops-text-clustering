# StackOverflow Oracle 运维文本聚类实验报告

## 摘要

本项目在三节点 Hadoop 3.3.6 / Spark 3.5.1 集群上，对 152,758 条 StackOverflow Oracle 问题完成数据入湖、清洗、EDA、特征工程、主题聚类、主题内 MinHashLSH、连通分量和 ORA 跨主题救援。

最终六组实验表明：K=50 Hybrid 覆盖最高，得到 46 对、42 个重复簇、87 个问题；在同一压缩方案下 K=150 与 K=200 的 42 条 Hybrid 边完全相同，说明 K 已收敛；2x 与 4x 压缩聚合指标相同，但边集合 Jaccard 为 0.7872，说明资源压缩会扰动少量候选。

## 1. 实验目标

课程要求使用集群完成大数据分析并进行系统演示。本项目目标是将本质相同但表达不同的 Oracle 运维问题聚到一起，同时形成可复现、可解释、可审计的 Spark 流水线。

原始文件约 589 MB，是嵌套 JSON 数组。项目先转 JSONL，再上传 HDFS。

## 3. 数据处理

清洗包括 HTML/实体/链接处理、技术 token 保留、高分回答选择和 ORA 错误码抽取。聚类文本为：

```text
title * 3 + body * 2 + tags + top_3_answers
```

评论噪声较高，只用于 EDA。

## 4. 特征工程

RegexTokenizer 与 StopWordsRemover 后生成两类特征：

- TF-IDF + L2 Normalizer：主题聚类。
- binary HashingTF：MinHashLSH。

默认维度 262144。ORA 码另存为 `array<string>`，不只依赖文本 token。

## 5. 最终算法

### 5.1 主题 Blocking

BisectingKMeans 先划分主题。MinHashLSH 不再全局运行，而是在每个 topic 内独立运行。主题按大小排序，较大 topic 先处理。

### 5.2 瘦 LSH Join

`approxSimilarityJoin` 只携带 doc_id 和 term_features。候选确定后再回填标题、分数、tokens、ORA 等字段，并用完整 token 集合重新计算 Jaccard。

### 5.3 ORA 规则

同主题候选共享 ORA 时加 0.10 boost，并支持 rescue floor。跨主题阶段按有效 ORA 码 join，要求 token Jaccard >= 0.55，或标签重合且 token Jaccard >= 0.50。参数 `title_sim_floor` 只是历史命名。

### 5.4 连通分量与 Lineage 截断

相似边写 Parquet 后重新读取，再进行标签传播；迭代内部使用 localCheckpoint。这样避免每轮连通分量重新执行上游 topic LSH。

### 5.5 大 K 向量 Folding

只对 BisectingKMeans 训练输入 folding：

- k150/k200：65536，4x。
- k150c2/k200c2：131072，2x。
- LSH term_features 保持 262144。

当前代码保留确定性 topic split 作为备用路径，但不属于最终六组结果。

## 6. 最终运行结果

| 运行 | K | 训练维度 | Baseline 对/簇/问题 | 救援记录 | 净新增边 | Hybrid 对/簇/问题 | Hybrid 平均相似度 |
|---|---:|---:|---:|---:|---:|---:|---:|
| k50 | 50 | 262144 | 43 / 39 / 81 | 3 | 3 | 46 / 42 / 87 | 0.7313 |
| k100 | 100 | 262144 | 41 / 37 / 77 | 3 | 3 | 44 / 40 / 83 | 0.7328 |
| k150 | 150 | 65536 | 38 / 36 / 74 | 6 | 4 | 42 / 40 / 82 | 0.7557 |
| k150c2 | 150 | 131072 | 38 / 36 / 74 | 5 | 4 | 42 / 40 / 82 | 0.7574 |
| k200 | 200 | 65536 | 37 / 35 / 72 | 7 | 5 | 42 / 40 / 82 | 0.7557 |
| k200c2 | 200 | 131072 | 38 / 36 / 74 | 5 | 4 | 42 / 40 / 82 | 0.7574 |

救援记录可能因同一 pair 共享多个 ORA 码而重复，净新增边才是图增量。

## 7. 稳定性分析

| 比较 | 共同边 | 集合 Jaccard |
|---|---:|---:|
| k150 vs k200（4x） | 42/42 | 1.0000 |
| k150c2 vs k200c2（2x） | 42/42 | 1.0000 |
| k150 4x vs k150c2 2x | 37/42 | 0.7872 |
| k200 4x vs k200c2 2x | 37/42 | 0.7872 |

同一压缩方案下 K=150 后结果完全收敛。不同压缩方案聚合指标一致，但每组有 5 条边差异，因此压缩在宏观上稳定、微观上不是完全无损。

## 8. 样例

K=50 最大簇包含 4 个 ORA-00907 “missing right parenthesis”的不同表达。跨主题救援包括 ORA-29280、ORA-30926、ORA-00906、ORA-04063、ORA-06508、ORA-28545 和 ORA-02063。

## 9. 工程实现评价

完成的关键工程优化包括：

1. JSON 数组流式转 JSONL。
2. HDFS/Parquet 分阶段落盘。
3. 主题内 LSH 降低全局候选压力。
4. 瘦 join 避免重字段进入 LSH cross-join。
5. 相似边物化截断 lineage。
6. 大 K 只压缩主题训练向量。
7. Raw Parquet 留集群，只提交派生结果表。

## 10. 评测边界

历史标签集含 90 条 LLM-as-a-Judge 辅助标签，总 precision 0.6667，Wilson 95% CI 为 [0.5642, 0.7555]；0.65 分组 precision 为 0.8125。标签没有逐条 review note，ORA match 子集只有 1 条，因此该评测仅作辅助。

没有全量重复关系 ground truth，所以不计算 recall/F1，不把“覆盖问题数”直接称为 recall，也不声称 K=50 是统计意义上的全局最优。

## 11. 最终选择

- 答辩主展示：k50 Hybrid，覆盖最高。
- 工程推荐：k150 4x，结果已收敛且平均相似度更高。
- k200：用于证明继续增大 K 没有收益。
- c2：用于展示压缩倍数对微观边集合的扰动。
