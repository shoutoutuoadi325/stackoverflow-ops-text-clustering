# 最终答辩讲稿

## 1. 项目完成内容

我们在三节点 Hadoop/Spark 集群上处理 152,758 条 StackOverflow Oracle 问题，完成数据入湖、清洗、特征工程、主题聚类、相似问题发现、ORA 跨主题救援和结果导出。

## 2. 为什么改造原流程

旧版主题聚类和全局 LSH 是两条平行链，主题结果没有参与去重。最终版本让主题聚类先做语义 blocking，再在 topic 内做 MinHashLSH。

## 3. 算法流程

文档使用标题 3x、正文 2x、标签和 Top 3 回答。TF-IDF 用于 BisectingKMeans，binary HashingTF 用于 LSH。候选后重新计算 token Jaccard，再用连通分量成簇。

## 4. ORA 创新

ORA 先抽成结构化数组，同主题候选共享 ORA 时加分。为补主题分桶漏检，再按 ORA 码构造跨主题边。过滤实际使用完整 token Jaccard 0.55，或标签重合且 token Jaccard 0.50。

K=50 从 39 簇、81 个问题提升到 42 簇、87 个问题；K=200 从 35 簇、72 个问题提升到 40 簇、82 个问题。

## 5. 六组结果

k50/k100 使用完整 262144 维主题特征；k150/k200 使用 65536；c2 使用 131072。主展示 k50 Hybrid 为 46 对、42 簇、87 个问题。

## 6. 新的稳定性结论

同一压缩方案下，K=150 与 K=200 的 42 条 Hybrid 边完全相同，说明继续增加 K 没有收益。

2x 与 4x 虽然都是 42 对、40 簇、82 个问题，但只共同 37 条边，集合 Jaccard 0.7872。所以宏观指标稳定，微观候选仍需审核。

## 7. Spark 工程创新

第一，LSH join 只携带 doc_id 和特征，候选后再回填重字段。第二，相似边写 Parquet 后重读，切断上游 DAG，避免连通分量每轮重算 LSH。第三，只压缩主题训练向量，不压缩 LSH 特征。

## 8. 最终选择

K=50 用于答辩展示，因为覆盖最高。K=150 4x 是工程推荐，因为结果已经收敛、平均相似度更高、主题训练资源更低。K=200 只用于证明收益收敛。

## 9. 评测边界

90 条历史标签来自 LLM-as-a-Judge 辅助评审，总 precision 0.6667。没有完整 ground truth，所以不计算 recall/F1，也不声称全局最优。

## 10. 总结

创新不在堆算法，而在把语义 blocking、领域补边、资源优化和可审计结果连成完整流水线，并用边集合而不只是计数验证稳定性。
