# 运维文本聚类项目答辩讲稿

建议总时长：PPT 讲解 6-8 分钟，Demo 2-3 分钟。

## 第 1 页：项目标题

各位老师好，我的项目是“运维文本聚类”，具体做的是基于 Hadoop 和 Spark 对 StackOverflow 中 Oracle Database 相关问答进行文本聚类和重复问题发现。

这个项目不是单机脚本，而是一条完整的大数据处理链路：从原始 JSON 数据入湖，到 Spark 清洗、特征工程、主题聚类、MinHashLSH 相似问题发现，最后导出成可以现场展示的 Demo。

这里有几个关键数字：数据集中有 152,758 个问题，总文本对象超过 90 万；最终用于展示的高召回配置发现了 16 个重复问题簇；整个过程在真实 YARN 集群上做过复核。

## 第 2 页：数据集

本项目的数据来自 Stack Exchange Data Dump，筛选的是 `oracle-database` 标签下的问题、回答和评论。

数据结构比较复杂，不只是问题标题和正文，还包括回答、问题评论、回答评论。问题数是 152,758，回答数是 203,393，两类评论合计超过 55 万。

这类数据的难点在于：原始 JSON 是大数组，不能直接高效并行读取；同时文本里有 HTML、代码块、错误码和技术标签，所以必须先做格式转换和清洗。

## 第 3 页：系统架构

整体流程是：原始 JSON 先转成 JSONL，再上传到 HDFS；Spark 读取后完成清洗和 Parquet 落盘；之后构造文本特征，分别进入主题聚类和相似问题发现；最终结果导出给 Demo。

集群环境是三台机器：master、worker1、worker2。Hadoop 版本是 3.3.6，Spark 是 3.5.1，Java 是 OpenJDK 8u412。

这里体现了 Hadoop 和 Spark 的分工：HDFS 负责可靠存储，YARN 负责资源调度，Spark 负责分布式计算和机器学习流程。

## 第 4 页：文本预处理

预处理阶段的目标是把真正有用的运维语义从 HTML 和普通自然语言噪声中抽出来。

我做了 HTML 清洗、代码块处理和文档重构。文档构造时，标题重复 3 次、正文重复 2 次，并拼接标签和前 3 个高分回答。这样做是因为标题和高分回答往往最能概括问题本质。

特征上有两套：TF-IDF 向量用于主题聚类，binary HashingTF 用于 MinHashLSH。后者更像集合表示，适合计算 Jaccard 相似度。

## 第 5 页：主题聚类

主题聚类部分使用的是 Spark ML 的 BisectingKMeans，默认设置为 k=50。

这一步的作用不是直接判断重复问题，而是帮助理解 Oracle 问答大致分布在哪些主题上，例如 SQL、PL/SQL、JDBC、Oracle 错误码、迁移等方向。

输出包括 cluster_id、doc_id、title、score、tags 和 cluster_top_terms。Demo 里也会展示这些主题聚类结果，作为宏观浏览入口。

## 第 6 页：重复问题发现算法

重复问题发现使用 MinHashLSH 加连通分量。

流程是：先把每个问题表示成 binary token 集合；MinHashLSH 生成候选相似问题对；然后用 token Jaccard distance 和 similarity 做二次校验；最后把相似边用 connected components 合并成重复问题簇。

代码现在支持两种 join 策略：一种是 Spark ML 官方的 `approxSimilarityJoin`，另一种是项目中保留的 bucket join。默认平衡配置是 similarity 大于等于 0.75；现场展示使用的是 0.65 高召回配置。

## 第 7 页：参数和结果

这里是最重要的结果页。

`0.65 / ht2 / bucket200` 这组在真实 YARN 全量数据上跑出了 16 对相似问题、16 个重复簇、32 道相关问题，耗时 1665 秒。它的特点是召回更多，适合现场展示。

`0.85 / ht4 / bucket300` 是严格高置信配置，只得到 3 对、3 个簇，但平均相似度更高。它适合说明 precision 和 recall 的取舍。

我没有声称某个参数是“全局最优 F1”，因为目前还没有人工标签。这里的结论是：选择高召回且可解释的结果做展示，同时保留严格配置作为对照。

## 第 8 页：样例结果

这页展示的是实际相似问题对。

比如 “join with lookup and groupby” 和 “join with lookup and group by” 的相似度是 0.8667；“Correlation and analytic function” 与 “Correlation function over analytic function” 的相似度是 0.85。

可以看到，这些样例不是随机相近，而是在标题语义、技术关键词、Oracle/SQL 上确实高度重合。顶层 `output/similar_pair_samples.csv` 和 `output/cluster_samples.csv` 已经同步为非空样例，评审可以直接打开复核。

## 第 9 页：工程取舍

这一页是我在 v1 优化后补充的工程验证。

课程方案推荐使用 Spark ML 的 `approxSimilarityJoin`，所以我已经把它接入到了 `cluster_lsh.py`，并且在 YARN smoke test 上验证通过。

但是我也做了全量压力测试：`0.75 / ht4 / approx300` 在当前集群资源下出现了 executor 心跳超时和 stage 9 长尾。运行约 29 分钟后，stage 9 只完成到 7/37，所以我主动停止，把它记录为工程压力测试，而不是最终展示结果。

因此最终答辩口径是：代码实现上支持官方 approx 路径；全量展示上选择更稳定、已经完整跑完的 bucket 路径。

## 第 10 页：Demo

现场 Demo 我建议使用静态页面，而不是现场实时跑 Spark。

原因是 Spark 作业会受 YARN 排队、网络、shuffle 长尾影响；而静态页面读取的是已经导出的真实结果，既稳定，又能证明结果来自完整计算链路。

演示顺序建议是：先展示数据核验和 EDA 卡片，再展示参数扫描汇总，然后展示重复问题簇和相似问题对，最后用关键词或 question_id 搜索一个样例。

## 第 11 页：评测边界

这一页是为了防止评审追问 precision、recall 和 F1。

目前项目已经生成了 82 条人工审核候选，但还没有填写 label，所以 precision 和 F1 显示为待人工审核。我没有伪造这些指标。

如果后续继续优化，应该先人工标注至少 50 到 100 对候选，再基于真实 precision 和候选覆盖量选择最终参数。

## 第 12 页：总结

总结来说，这个项目完成了真实数据核验、真实集群部署、Spark 分布式处理、文本特征工程、主题聚类、相似问题发现、重复簇生成和 Demo 展示。

我认为这个项目最重要的点不是某一个指标特别好看，而是每个关键数字都有来源：来自原始数据核验文件、Spark/YARN 输出、样例 CSV 或 verification 日志。

后续可以继续做三件事：补人工标签，继续参数网格搜索，引入 Sentence-BERT 这类语义向量来提升近义表达的召回。

## 可能被问到的问题

### 为什么 0.65 比 0.85 更适合展示？

0.85 更严格，结果更少，只发现 3 对；0.65 能展示 16 对和 16 个簇，更适合说明系统效果。答辩时不能说 0.65 一定精度最高，只能说它更适合高召回展示。

### 为什么没有 precision / F1？

precision 和 F1 必须依赖人工标签。项目已经生成 `evaluation/review_candidates.csv`，但 label 尚未审核，所以不伪造指标。

### 为什么不直接用 approxSimilarityJoin 全量结果？

代码已经支持并通过了 YARN smoke test。但全量 `0.75/ht4/approx` 在当前资源下出现长尾和 executor 心跳超时，约 29 分钟后仍处于主 join 阶段。因此最终展示采用已完整跑完、可复现的 bucket 路径。

### 这个项目体现了“大数据”在哪里？

体现在三个方面：第一，原始数据规模和嵌套结构需要入湖和格式转换；第二，清洗、特征工程和聚类在 Spark on YARN 上运行；第三，中间和最终结果都写入 HDFS/Parquet，支持断点复跑和复核。

### 后续最值得做的优化是什么？

优先补人工审核标签，因为没有标签就不能判断真实 precision。其次是继续跑参数网格，最后再考虑 Sentence-BERT 等语义向量。
